This candidate gives the cooperative work deadline and wall alarm a distinct exception. Before a new chunk, an expired budget ends the worker successfully only if earlier chunks committed. During preparation, that exception closes and discards the interrupted database connection, aborting its entire unfinished transaction, and returns only the earlier committed counts and cursor as `budget_deferred`. Closing the driver explicitly makes a close error propagate rather than being suppressed by pool invalidation. The next separately admitted request resumes from the saved cursor. Cleanup failure, uncertain commit, hard CPU signal, parser/checksum errors and an inside-chunk memory hold still fail. An expired first chunk still fails, preventing a no-progress success loop.

The 60-second cooperative wall limit, 45-second cooperative CPU limit, 70-second alarm, 60/65-second hard CPU limits, 750MiB worker memory guard, queue ownership, SQL timeouts and five-chunk maximum remain unchanged. The parser and its fingerprint are unchanged, so existing prepared originals remain eligible for independent source verification. The change does not speed up a single expensive operation or prove that every future source fits one chunk. It also does not resolve the separate API memory-growth attribution question.
